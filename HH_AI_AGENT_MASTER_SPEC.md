## 1. Цель и главный принцип

Приложение помогает **одному человеку** находить подходящие вакансии на hh.kz, понимать, стоит ли откликаться, писать персональное сопроводительное под каждую вакансию и отправлять отклик — с сохранением всей истории.

Это **не** скрипт «нашёл → нажал откликнуться». Пайплайн:

```
Собрать → Дедуплицировать → Отфильтровать без LLM → Понять и оценить → Решить
   → Написать письмо → Проверить факты → Откликнуться → Отследить результат
```

Три правила, которые нельзя нарушать:

1. **Никогда не выдумывать факты о кандидате.** Всё, что попадает в письмо, должно выводиться из текста резюме или списка Allowed Facts.
2. **Никогда не отправлять отклик дважды на одну вакансию.**
3. **Никогда не импровизировать в непонятной ситуации.** Не тот экран, не найден селектор, капча, неизвестная форма → остановка со статусом «Нужно действие пользователя».

## 2. Ограничения железа — читать до проектирования

Целевая машина:

```
CPU:  Intel i5-9300H (4 ядра / 8 потоков)
GPU:  NVIDIA GTX 1650 Mobile — 4 ГБ VRAM
RAM:  16 ГБ
OS:   Linux Mint 22.3 (Ubuntu 24.04)
```

Это не абстрактный контекст, из него следуют жёсткие архитектурные требования:

**4 ГБ VRAM.** Модель `qwen3:4b-instruct` в квантовании q4 занимает ~2.6 ГБ весов, остальное — KV-кэш. Модели больше 4B на GPU не помещаются и уходят в CPU, где скорость падает в 5–10 раз.

**Контекст 8192 токена, не больше.** Обязательно выставлять `num_ctx` явно — дефолт Ollama 4096 молча обрежет промпт, и модель перестанет «видеть» половину вакансии. Описание вакансии обрезать до `max_vacancy_chars` (настройка, дефолт 6000 символов).

**Никаких параллельных LLM-вызовов.** `OLLAMA_NUM_PARALLEL=1`. AI-джобы обрабатывает ровно один воркер. Два одновременных запроса на 4 ГБ VRAM = выгрузка модели и деградация в CPU.

**Держать модель загруженной.** `OLLAMA_KEEP_ALIVE=30m`, иначе каждая вакансия начинается с 10–15 секунд загрузки модели в память.

**Реальные тайминги** (локальная модель, для оценки UX, не для тестов):

```
чтение промпта (~5000 токенов)    15–25 сек
генерация JSON-ответа (~600 ток.) 20–30 сек
────────────────────────────────────────────
один LLM-вызов                    ~40 сек
вакансия (анализ + письмо + факт-чек) ~2 мин
прогон на 25 новых вакансий       ~50 мин
```

Из этого следует: показывать прогресс, уметь ставить на паузу, уметь продолжить с места остановки. Пользователь не будет сидеть и смотреть.

**RAM 16 ГБ.** Одновременно живут: Ollama с моделью (~4 ГБ), видимый Chromium (~1.5 ГБ), backend, Vite dev server. Не держать в памяти списки вакансий целиком, не грузить все события прогона в один ответ API.

## 6. Модель данных

Одна база: `data/jobpilot.db`. Одна цепочка миграций Alembic. Никаких отдельных БД на резюме.

### Сущности

```
Резюме (resumes)
├── Выжимка (хранится в самом резюме, JSON)
├── Навыки (resume_skills) — производные от выжимки, для фильтров и статистики
├── Allowed Facts (текстовое поле)
├── Примеры писем (letter_examples)
└── Поисковые профили (search_profiles)
     └── Запросы (search_queries)

Вакансия (vacancies)                    ← факты с HH, одна строка на hh_id
└── Решение по резюме (resume_vacancies) ← статус, скор, причина — своё на каждое резюме
     ├── Письма (letters)
     └── Отклик (applications)          ← глобально не более одного на вакансию

Прогон (runs)
├── Задачи (jobs)      ← персистентная очередь
└── События (run_events)

Правила по компаниям (company_rules)
Провайдеры LLM (llm_providers)
Промпты (prompts)
Настройки (settings)
```

## 7. Резюме — одна сущность

Раньше профиль кандидата и резюме HH были разными объектами, а опыт/проекты/достижения лежали в четырёх таблицах с отдельными экранами. Теперь всё это — **одно резюме**.

Экран «Резюме» содержит:

```
Название                 «Backend Node.js»
Текст резюме             большое textarea — сюда вставляется резюме с HH как есть
Allowed Facts            textarea, по факту на строку
Ссылка на резюме HH      https://hh.kz/resume/...
Языки писем              [x] ru  [x] kk  [ ] en
Выжимка                  JSON, редактируемый, кнопка «Пересобрать»
Навыки                   чипсы, правятся руками
```

### Выжимка (digest) — зачем она

Текст резюме — это 3000–4000 токенов. Контекст модели — 8192. Если пихать полный текст в каждый LLM-вызов, происходит две плохие вещи: половина окна уходит на резюме (медленно, ~20 секунд только на чтение промпта, и так трижды на каждую вакансию), а маленькая модель начинает терять детали в длинном тексте.

Поэтому при сохранении резюме делается **один разовый** LLM-вызов, который сжимает текст в структуру:

```json
{
  "title": "Fullstack Developer (Middle+)",
  "years_total": 4,
  "level": "middle+",
  "core_stack": ["TypeScript", "Vue", "Node.js", "NestJS", "Go", "PostgreSQL"],
  "additional": ["Python", "FastAPI", "Docker", "Redis", "Kafka", "React", "Nuxt"],
  "domains": ["REST API", "микросервисы", "CI/CD", "инфраструктура"],
  "languages": {"kk": "native", "ru": "B2", "en": "B1"},
  "highlights": [
    "миграция backend с Yii2 на Node.js/Express",
    "микросервисы на Go/Fiber",
    "настройка CI/CD в GitLab CI и GitHub Actions"
  ],
  "location": "Усть-Каменогорск",
  "relocation": ["Алматы", "Астана"],
  "work_formats": ["удалённо", "гибрид", "офис"]
}
```

Это ~600 токенов вместо 3500.

**Где что используется:**

```
Анализ вакансии    → выжимка          (детали не нужны, нужен стек и уровень)
Письмо             → выжимка + полный текст резюме + Allowed Facts
Факт-чек           → выжимка + Allowed Facts
Ответ на вопрос    → выжимка + полный текст резюме
```

Выжимка редактируется руками — если модель что-то вытащила криво, ты правишь JSON в UI, и дальше используется твоя версия. Кнопка «Пересобрать выжимку» перегенерирует её из текста.

`core_stack` и `additional` дополнительно раскладываются в `resume_skills` — это нужно не модели, а hard-фильтрам (проверить наличие ключевого слова без LLM) и статистике («какие технологии чаще всего требуют в вакансиях, которых у меня нет»).

### Действия с резюме

```
Редактировать · Дублировать · Архивировать · Удалить
```

Удаление — только через подтверждение и только если по резюме нет отправленных откликов. Иначе архивирование.

В шапке приложения — селектор активного резюме. Всё в приложении (вакансии, поисковые профили, письма, статистика) фильтруется по нему. **Работа идёт по одному резюме за раз** — параллельные прогоны разных резюме в v1 не поддерживаются.

## 9. Браузер и сессия HH

Playwright, видимый Chromium, постоянный профиль:

```python
context = await playwright.chromium.launch_persistent_context(
    user_data_dir="data/browser/default",
    headless=False,
    viewport={"width": 1440, "height": 900},
)
```

Профиль хранит cookies и localStorage, поэтому логин переживает перезапуск приложения.

**Первый запуск:** открывается Chromium, пользователь логинится руками. Бот ждёт и определяет факт логина по наличию элемента личного кабинета.

**Если HH требует повторный вход, показывает капчу, просит SMS или любое подтверждение** — бот не пытается это обойти, не кликает, не ждёт бесконечно. Ставит статус `NEEDS_USER_ACTION`, пишет событие, показывает в UI:

```
⚠ Требуется вход в HH
   [Открыть браузер]   [Проверить снова]
```

Обход капчи, антибот-защиты, подмена fingerprint, ротация прокси — **не делаем**. Задержки между действиями (§22) — это уважение к чужому серверу, а не маскировка.

### Селекторы

Все селекторы HH — только в `browser/selectors.py`, одним классом с константами. Ни одного `page.locator(...)` со строкой внутри бизнес-логики. Когда HH поменяет вёрстку (а он поменяет), чинится один файл.

## 10. Сбор вакансий и дедупликация

Это место, где экономится основное время прогона.

### Порядок действий

```
1. Открыть страницу выдачи поиска
2. Собрать со страницы ТОЛЬКО список hh_id + минимум полей
   (заголовок, компания, зарплата, дата) — карточки не открывать
3. SELECT hh_id FROM vacancies WHERE hh_id IN (...)
   → известные: обновить last_seen_at, seen_count, идти дальше
   → новые: только они попадают в очередь
4. Прогнать hard-фильтры по тому, что уже видно в выдаче
   (зарплата, дата, компания, стоп-слова в заголовке)
   → отсеянные сохранить со статусом и причиной, карточку не открывать
5. Открыть карточку только у выживших
```

Отсечка на шаге 3 — причина, по которой второй прогон за день займёт 10 минут вместо часа.

### Три уровня «уже»

```
уже видели       vacancies.hh_id существует           → не открываем карточку
уже решили       resume_vacancies.status заполнен      → не гоняем LLM
уже откликнулись applications.vacancy_id существует    → не жмём «Откликнуться» никогда
```

Первые два — на уровне резюме: одна вакансия может быть отклонена для Go-резюме и готова к отклику для Fullstack. Третий — **глобальный**: повторный отклик на ту же вакансию невозможен ни при каких настройках, с любого резюме.

### Извлечение данных вакансии

Основной путь — вытащить из страницы встроенный JSON с данными вакансии через `page.evaluate`. Он устойчивее CSS-классов, которые меняются каждый релиз HH.

Фолбэк — DOM-селекторы. Логика:

```
попытка JSON → не нашли или не распарсился → попытка DOM → не вышло →
статус PARSE_FAILED, скриншот, событие, идём к следующей вакансии
```

Оба пути живут в `browser/extract.py`, наружу отдают одну и ту же Pydantic-модель. Сырой JSON со страницы складывать в `vacancies.raw_json` — пригодится, когда понадобится поле, о котором сейчас не подумали.

### Пересмотр отфильтрованных

Если поменять фильтры или порог скора, старые вакансии сами не пересмотрятся — они уже лежат со статусом «отклонена». Поэтому в UI обязательна кнопка:

```
[Пересмотреть отклонённые]  — прогнать заново по текущим правилам
```

Описание уже сохранено в БД, так что браузер для этого не нужен — только фильтры и LLM. Без этой кнопки можно один раз выставить минималку 100к, отсечь половину рынка и никогда об этом не узнать.

## 11. Hard-фильтры (без LLM)

Всё, что можно решить кодом, решается кодом. LLM дорогая (40 секунд) и не нужна там, где есть точные данные.

### Зарплата

```
min_salary, currency, allow_unknown_salary
```

- Сравнение по `salary_from`. Если указана только `salary_to` — сравнивается она.
- **Валюта.** Вакансии бывают в KZT, RUB, USD, EUR. Курсы хранятся в настройках (`settings.currency_rates`), правятся руками, обновляются раз в месяц — никаких внешних API за курсом в v1. Если курса для валюты нет → вакансия не отсекается, идёт дальше с пометкой `salary_unconverted`.
- **Gross / net.** Если `salary_gross = true`, перед сравнением умножить на `1 - settings.tax_rate` (дефолт 0.10 для КЗ). Настройка редактируется.
- Зарплата не указана → по `allow_unknown_salary`.

### Формат работы

```
REMOTE_ONLY | REMOTE_OR_HYBRID | ANY
```

### Стоп-слова и обязательные слова

Проверка по заголовку и описанию, регистронезависимо. Стоп-слова применяются к заголовку ещё на этапе выдачи (до открытия карточки).

### Опыт и свежесть

Диапазоны опыта HH; `max_age_days` по `published_at`.

### Язык описания

Определяется **кодом, не моделью**: доля кириллицы, наличие казахских специфических букв (ә, ғ, қ, ң, ө, ұ, ү, һ, і), иначе английский. По языку **не фильтруем** — вакансия читается в любом случае. Язык нужен только чтобы выбрать язык письма (§17).

Каждый отсев пишет `skip_reason` и человекочитаемый `skip_details`. Вакансия не удаляется никогда.

## 12. Правила по компаниям

```
Тип совпадения   CONTAINS | EQUALS
Значение         vash
Регистр          не учитывать
Действие         ПРОПУСТИТЬ | ВСЕГДА НА ПРОВЕРКУ | ПОВЫСИТЬ ПРИОРИТЕТ | ШТРАФ К СКОРУ
Дельта скора     +20 / -10   (для двух последних действий)
```

`CONTAINS "vash"` ловит «Vash Group», «VASH COMPANY», «ТОО Vash».

Правило может быть общим (`resume_id = NULL`) или только для одного резюме.

Штраф и бонус применяются **после** получения скора от модели и **до** сравнения с порогами. Вакансия при `ПРОПУСТИТЬ` сохраняется со статусом «отклонена / фильтр компаний».

В UI — кнопка **«Проверить правило»**: вводишь название компании, видишь, сработает или нет.

## 13. Подозрительные вакансии

Отдельный механизм, не путать с фильтрами. Такие вакансии **не отбрасываются молча** — они сохраняются со статусом «Подозрительная» и попадают в отдельный список, чтобы их можно было просмотреть глазами. Бот на них не откликается и идёт дальше.

### Жёсткие правила (кодом, без LLM)

```
описание короче 300 символов
компания не указана / «Частное лицо»
в описании нет требований, только «звоните в WhatsApp / Telegram»
кнопка отклика ведёт на внешний сайт
```

### Признаки, которые определяет модель

Модель возвращает `is_suspicious` и список причин. Промпт редактируемый, дефолт покрывает:

```
1. Слишком хорошие условия при малом объёме работы
   («2 часа в день», «свободный график», «доход от 500 000»)
2. Высокая зарплата при низких требованиях к опыту
   (junior / без опыта + зарплата уровня senior)
3. Требуют документы до трудоустройства
   (паспорт, ИИН, скан удостоверения, фото с документом)
4. Работа без трудового договора
   («оформление по договорённости», «работа неофициально»)
5. Требуют оформить ИП / самозанятость вместо трудоустройства
   как условие входа, а не как форму оплаты
6. Требуют вложить свои деньги
   (взнос, оплата обучения, покупка оборудования, «инвестиция в развитие»,
    «сначала вложишь — потом заработаешь больше»)
7. Работа на другую страну / релокация без обсуждения,
   выплаты через третьи страны, криптовалютой
8. Нет конкретики: не сказано, что делать и какой продукт
9. Обещания дохода без описания обязанностей
10. Просят перейти в мессенджер до собеседования
```

Ответ модели:

```json
{
  "is_suspicious": true,
  "suspicious_reasons": [
    "Требуют оформить ИП до начала работы",
    "Обещают 800 000 KZT при требовании 'без опыта'"
  ]
}
```

Это часть общего вызова анализа (§15), отдельный LLM-запрос не делается.

В UI подозрительные вакансии — отдельный пункт бокового меню со своим счётчиком. Из карточки можно нажать «Это нормальная вакансия» — тогда флаг снимается и вакансия возвращается в общий поток.

## 14. Провайдеры LLM и маршрутизация по шагам

### Провайдеры

Единый интерфейс `LLMProvider.complete(prompt, schema, **opts) -> dict`. Пять реализаций:

| Тип | Как работает | Аутентификация |
|---|---|---|
| `ollama` | HTTP на `localhost:11434` | не нужна |
| `anthropic` | официальный SDK `anthropic` | API-ключ |
| `openai` | официальный SDK `openai` | API-ключ |
| `openrouter` | HTTP, OpenAI-совместимый | API-ключ |
| `cli` | `subprocess`: `claude -p` / `codex exec` | подписка Claude / ChatGPT |

**Про `cli`.** Claude Code и Codex CLI умеют неинтерактивный режим и биллятся по подписке, а не по API-ключу:

```bash
claude -p "<промпт>" --output-format json
codex exec "<промпт>"
```

Это официально поддерживаемый сценарий. Реализация — `asyncio.create_subprocess_exec`, чтение stdout, таймаут, парсинг JSON. Настройки провайдера: `command` (`claude` / `codex`), `args`, `timeout`.

**Чего делать нельзя ни при каких условиях:** автоматизировать веб-интерфейсы chatgpt.com или claude.ai, перехватывать токены сессии, использовать неофициальные обёртки над ними. Это нарушение условий использования и прямой путь к блокировке аккаунта.

### Модели по умолчанию

```
ollama      qwen3:4b-instruct        num_ctx 8192, temperature 0.3
anthropic   claude-haiku-4-5         для анализа (дёшево)
            claude-sonnet-5          для писем
openai / openrouter                  модель выбирается пользователем
cli         модель определяет сам CLI
```

Порядок цен Anthropic для оценки: Haiku 4.5 — $1 / $5 за миллион входных / выходных токенов; Sonnet 5 — $3 / $15. При ~6000 входных и ~1000 выходных токенов на вызов один прогон на 25 вакансий обходится примерно в $0.8 на Haiku. Это к тому, что внешний API — не «дорого», а «дешевле часа ручного отбора».

### Маршрутизация — главное здесь

**Провайдер выбирается не глобально, а на каждый шаг пайплайна.** В UI — таблица с выпадающими списками:

```
Шаг                     Провайдер            Модель
────────────────────────────────────────────────────────────
Выжимка резюме          [Ollama        ▼]   qwen3:4b-instruct
Анализ вакансии         [Ollama        ▼]   qwen3:4b-instruct
Сопроводительное письмо [Claude CLI    ▼]   —
Проверка фактов         [Claude CLI    ▼]   —
Ответы на вопросы       [Claude CLI    ▼]   —
                                             [Проверить все]
```

Смысл: анализ гоняется 25 раз за прогон и ему достаточно локальной модели — это дёшево и приватно. Письмо пишется один раз на вакансию, и разница в качестве между 4B и нормальной моделью там видна сразу. Платишь только там, где это заметно.

Хранится в `settings.llm_routing`:

```json
{
  "resume_digest": 1,
  "analyze": 1,
  "letter": 3,
  "fact_check": 3,
  "answer_question": 3
}
```

где значения — `llm_providers.id`. Кнопка «Проверить» у каждого провайдера делает тестовый вызов и показывает ответ и время.

### Если провайдер недоступен

Нет интернета, кончился лимит подписки, CLI вернул ошибку, Ollama не запущен:

```
1. Одна повторная попытка через 5 секунд
2. Если снова ошибка → прогон ОСТАНАВЛИВАЕТСЯ
   status = STOPPED, stop_reason = PROVIDER_UNAVAILABLE
3. Текущая вакансия остаётся в очереди в состоянии PENDING
4. В UI: «Прогон остановлен: провайдер писем недоступен» + текст ошибки
5. Кнопка [Продолжить] — прогон возобновляется с той же вакансии
```

Молчаливого фолбэка на слабую модель нет: лучше остановиться, чем разослать десяток писем худшего качества, не сказав об этом.

## 15. Пайплайн анализа

Один LLM-вызов на анализ вместо двух. Раньше было «извлечь требования» → «сопоставить с кандидатом»; на локальной 4B это удвоенное время и удвоенный шанс получить невалидный JSON ради структуры, которую тут же скармливают дальше.

```
Вакансия (описание, обрезанное до max_vacancy_chars)
   + выжимка резюме
   + allowed facts
        ↓
   [ АНАЛИЗ ]  ← один вызов
        ↓
   requirements + оценка + red flags + подозрительность + скрытые инструкции
        ↓
   [ РЕШЕНИЕ ] ← чистая функция, без LLM
        ↓
   ПРОПУСТИТЬ / НА ПРОВЕРКУ / ОТКЛИКНУТЬСЯ
```

### Схема ответа анализа

```json
{
  "profession_match": true,
  "can_do_job": true,
  "score": 86,
  "score_breakdown": {
    "profession": 100,
    "stack": 90,
    "experience": 75,
    "responsibilities": 85
  },
  "required_skills": ["Node.js", "PostgreSQL", "Docker"],
  "preferred_skills": ["Kafka", "Kubernetes"],
  "matched_skills": ["Node.js", "PostgreSQL", "Docker"],
  "missing_skills": ["Kubernetes"],
  "critical_missing": [],
  "red_flags": ["Требуется знание 1С на уровне разработчика"],
  "green_flags": ["Удалённо", "Core stack совпадает"],
  "is_suspicious": false,
  "suspicious_reasons": [],
  "hidden_instructions": [],
  "employer_questions_detected": false,
  "reason": "Стек полностью совпадает, опыт 4 года при требовании 3+."
}
```

Чего в схеме **нет** и не должно быть: `salary_score`, `work_format_score`, `salary_match`. Зарплата и формат уже проверены hard-фильтрами точно — спрашивать про них модель значит давать ей возможность соврать.

`can_do_job` — это не «много слов совпало», а «сможет реально делать основные обязанности». Это должно быть прямо сказано в промпте.

### Валидация

Каждый ответ модели валидируется Pydantic. Если невалиден:

```
1. Один повторный запрос с добавкой «Верни строго JSON по схеме, без пояснений»
2. Снова невалиден → статус ANALYSIS_FAILED, событие с сырым ответом,
   переход к следующей вакансии
3. Автоотклик при ANALYSIS_FAILED невозможен
```

Сырой ответ модели всегда сохраняется в `resume_vacancies.analysis_json` вместе с разобранным — при разборе проблем видно, что именно вернула модель.

### Решение (без LLM)

```python
if hard_filters_failed or company_rule == SKIP: → ПРОПУСТИТЬ
if is_suspicious:                               → ПОДОЗРИТЕЛЬНАЯ
if not profession_match or not can_do_job:      → ПРОПУСТИТЬ
if critical_missing:                            → ПРОПУСТИТЬ
score = llm_score + company_score_delta
if score < min_score:                           → ПРОПУСТИТЬ
if score < auto_apply_score:                    → НА ПРОВЕРКУ
if employer_questions and not answerable:       → НУЖНЫ ДАННЫЕ
                                                → ОТКЛИКНУТЬСЯ
```

Пороги `min_score` (дефолт 75) и `auto_apply_score` (дефолт 90) — настройки резюме.

## 16. Скрытые инструкции в описании вакансии

Работодатели вставляют в текст вакансии проверки на внимательность:

```
«Если дочитали до конца — напишите в сопроводительном слово Сыр»
«В начале письма укажите желаемую зарплату»
«Ответьте, что такое SOLID, в сопроводительном»
```

Ровно для того, чтобы отсеять шаблонные отклики. Модель обязана их находить — это одна из самых ценных функций всего бота, потому что при ручном отклике такое пропускается чаще, чем при автоматическом.

Поле в ответе анализа:

```json
"hidden_instructions": [
  "написать в сопроводительном слово 'Сыр'",
  "указать в начале письма желаемую зарплату"
]
```

Список передаётся в промпт письма как **обязательный к исполнению** блок. После генерации письма — программная проверка: если инструкция содержит конкретное слово в кавычках, проверить его наличие в тексте. Не выполнено → регенерация (одна попытка) → если снова нет, письмо идёт на ручную проверку с пометкой.

В карточке вакансии скрытые инструкции показываются отдельным блоком с иконкой — чтобы при ручном отклике их тоже было видно.

## 17. Сопроводительные письма

**На каждую вакансию — своё письмо.** Один шаблон на всех запрещён.

Модель получает:

```
выжимка резюме
полный текст резюме
allowed facts
вакансия: заголовок, компания, описание
результат анализа: совпавшие навыки, green flags
скрытые инструкции
2–3 примера писем пользователя (только как ориентир стиля)
язык письма
целевая длина
```

### Язык

Определяется языком **описания** вакансии (не заголовка — в IT заголовок часто английский при русском описании), из числа разрешённых в резюме.

Отдельно: локальная 4B-модель пишет по-казахски заметно хуже, чем по-русски. Если для казахской вакансии выбран `kk`, а провайдер — локальный, показывать в UI предупреждение и предлагать написать письмо на русском (в Казахстане это норма).

### Длина

Настройка, дефолт 900–1400 символов. Передаётся в промпт и проверяется кодом после генерации.

### Действия в UI

```
Написать самому · Сгенерировать · Перегенерировать
Короче · Более технично · Более живо · Своя инструкция
Редактировать · Сохранить · Откликнуться
```

Все версии сохраняются с указанием источника (`AI`, `MANUAL`, `AI_EDITED`, `AI_REWRITE`) и того, какая именно была отправлена.

Ручной режим должен позволять написать письмо полностью самому — Playwright тогда просто вставляет готовый текст.

### Если поля письма нет

Часть вакансий не имеет поля сопроводительного. Тогда отклик уходит без письма, в истории — пометка `LETTER_NOT_SUPPORTED`.

### Примеры писем

CRUD в UI: `название`, `категория`, `тон`, `текст`, `активен`, `предпочтительный`. Категории: Backend, Fullstack, Go, Стартап, Энтерпрайз, Общий.

В промпт подставляются 2–3 примера, подобранные по категории. В промпте прямо сказано: использовать как ориентир по тону, структуре и длине, **не копировать формулировки**.

## 18. Проверка фактов

После генерации — второй проход другим промптом (провайдер настраивается отдельно, см. §14).

```json
{
  "valid": false,
  "unsupported_claims": ["У меня большой опыт AWS"],
  "suggested_fixes": ["Удалить утверждение об AWS"]
}
```

Перед LLM-проверкой — **быстрая программная**: из письма достаются упоминания технологий по словарю (`resume_skills` + список известных технологий) и сверяются с резюме. Если в письме есть технология, которой нет ни в резюме, ни в allowed facts — это найдётся мгновенно и бесплатно, до всякой модели.

Порядок: словарная проверка → LLM-проверка → результат.

При `valid = false` автоотклик запрещён. Вакансия уходит на ручную проверку с показанной причиной.

## 19. Вопросы работодателя

Часть вакансий добавляет к отклику вопросы. Три категории, обрабатываются по-разному.

### 1. Вопросы на знание — отвечает модель

```
«Что такое SOLID?»
«Чем отличается REST от GraphQL?»
«Что такое Python?»
```

Тут выдумывать нечего, это проверка компетенции. Модель отвечает коротко и по делу.

### 2. Вопросы о кандидате — отвечает модель, если ответ есть в резюме

```
«Сколько лет опыта с Node.js?»
«Уровень английского?»
«Готовы к переезду?»
«Желаемая зарплата?»
```

Отвечает **только если ответ выводится из резюме или allowed facts**. Не выводится — статус «Нужны данные», отклик не отправляется.

### 3. Личные данные — не отвечает никогда

Жёсткое правило **кодом**, не промптом. Список запрещённых полей в `core/personal_data.py`:

```
номер паспорта / удостоверения, ИИН, адрес проживания,
банковские реквизиты, номер карты, фото документов,
данные родственников, СНИЛС, дата рождения полностью
```

Совпадение → статус `NEEDS_USER_ACTION` с причиной «Запрошены личные данные», отклик не отправляется, вакансия остаётся в списке для ручной обработки.

Разрешено подставлять из резюме: телефон, email, город, ссылки на GitHub и портфолио.

### Настройка

```
answer_employer_questions:  выключено (по умолчанию) | включено
```

Пока выключено — любая вакансия с вопросами уходит в «Нужны данные». Включается, когда пользователь посмотрит на качество ответов.

### Внешние формы

Если отклик уводит на сайт компании или внешнюю ATS — бот не заполняет ничего. Статус «Внешний отклик», ссылка, ручная обработка.

## 20. Режимы работы

Две независимые оси. Обе видны в шапке приложения крупно.

### Ось 1 — насколько бот самостоятелен

**Ручной.** Бот ищет, фильтрует, анализирует, может сгенерировать письмо. Отклик **не отправляет никогда**. Всё решает пользователь.

**Полуавтомат.**

```
скор < 75          → отклонена
75 ≤ скор < 90     → на проверку (Очередь проверки)
скор ≥ 90          → на проверку, но помечена как рекомендованная
```

Отклик отправляется по кнопке. В очереди есть `Откликнуться и далее` — один клик на вакансию.

**Автомат.** Бот доходит до отправки сам. Разрешён только при выполнении **всех** условий:

```
profession_match = true
can_do_job = true
score ≥ auto_apply_score
critical_missing пусто
is_suspicious = false
hard-фильтры пройдены
правила компаний пройдены
проверка фактов пройдена
сессия HH активна
отклика на эту вакансию ещё не было
форма отклика распознана
вопросов работодателя нет (или все отвечены и разрешены)
режим LIVE
лимиты не исчерпаны
```

Любое невыполненное условие → вакансия уходит на ручную проверку, бот идёт дальше.

### Ось 2 — доходит ли дело до реальной отправки

**DRY_RUN.** Всё по-настоящему: реальный HH, реальные вакансии, реальные письма, реальная форма отклика открывается. Финальная кнопка **не нажимается**. Результат сохраняется как «отклик подготовлен».

**LIVE.** Отклики отправляются.

**Первый прогон любого нового резюме принудительно идёт в DRY_RUN.** Переключение в LIVE — руками, после того как пользователь посмотрит несколько подготовленных писем. Это защита от ситуации «настроил не то и разослал 20 откликов».

### Лимиты

```
max_applications_per_run    20
max_applications_per_day    30
delay_between_vacancies     3–8 сек (случайно)
delay_before_apply          2–5 сек
delay_after_apply           10–20 сек
```

Все редактируются в UI. Это ограничение нагрузки, а не маскировка.

## 21. Отклик и защита от дублей

Перед нажатием кнопки отправки:

```
1. SELECT * FROM applications WHERE vacancy_id = ?   → есть → стоп, DUPLICATE
2. Проверить на странице признак «Вы уже откликались» → есть → записать
   в applications как внешний отклик, статус ALREADY_APPLIED, идти дальше
3. Проверить, что открыта форма именно этой вакансии (сверить hh_id в URL)
4. Проверить, что режим LIVE
5. Проверить лимиты
6. Вставить письмо, нажать отправить
7. Дождаться подтверждения на странице
8. Записать в applications ДО того, как считать операцию успешной
```

**Ретрай сетевой ошибки никогда не повторяет нажатие отправки вслепую.** Если после нажатия связь оборвалась и результат неизвестен — статус `APPLICATION_STATE_UNKNOWN`, скриншот, ручная проверка. Лучше один неясный отклик, чем два реальных.

## 22. Прогоны, очередь, остановки

### Очередь — в базе, не в памяти

Таблица `jobs`. Это принципиально: прогон должен переживать паузу, остановку, падение приложения и продолжаться с того места, где встал.

Типы задач:

```
SEARCH → FETCH_VACANCY → FILTER → ANALYZE → GENERATE_LETTER
       → FACT_CHECK → APPLY → SYNC_STATUS
```

Состояния задачи: `PENDING → RUNNING → DONE | FAILED | SKIPPED`.

Один воркер, последовательно. Параллелизм невозможен — упрёмся в VRAM (§2).

### Управление

```
[Запустить]  [Пауза]  [Продолжить]  [Остановить]
```

**Пауза.** Текущая задача доводится до конца, следующая не берётся. Состояние `PAUSED`.

**Продолжить.** Берём следующую `PENDING` задачу того же прогона. Ничего не переделываем заново.

**Остановить.** Новые задачи не берутся, события сбрасываются в БД, состояние сохраняется, браузер закрывается корректно, прогон завершается со `stop_reason`.

### Остановка по ошибкам

**5 ошибок подряд → полная остановка прогона.**

Считаются ошибки любого шага. Успешно обработанная вакансия сбрасывает счётчик.

При остановке сохраняется:

```
stop_reason        = TOO_MANY_ERRORS
last_error_code    = BROWSER_SELECTOR_NOT_FOUND
last_error_step    = OPEN_APPLY_FORM
+ скриншот последней ошибки
+ последние 5 ошибок в событиях
```

В UI — красная плашка, по-русски, с указанием шага и скриншотом:

```
⛔ Прогон остановлен: 5 ошибок подряд
   Шаг: открытие формы отклика
   Код: BROWSER_SELECTOR_NOT_FOUND
   [Скриншот]  [События]  [Продолжить]
```

Смысл в том, чтобы по этому экрану было сразу понятно, что чинить: сменилась вёрстка HH, отвалился Ollama или закончилась сессия.

### Прогон

```
runs: id, resume_id, mode, runtime_mode, status,
      started_at, ended_at, stop_reason,
      counters_json {found, new, filtered, analyzed, suitable,
                     review, applied, skipped, suspicious, errors},
      last_error_code, last_error_step
```

### Восстановление после падения

При старте приложения:

```
runs в статусе RUNNING     → INTERRUPTED
jobs в состоянии RUNNING   → PENDING (можно взять заново)
applications без подтверждения → APPLICATION_STATE_UNKNOWN, на ручную проверку
```

Задачу типа `APPLY` **никогда** не возвращать в `PENDING` автоматически — только через проверку по §21.

### Планировщик

Ручной запуск, запуск конкретного поискового профиля, запуск всех включённых. Расписание — простой интервал (раз в N часов), выключается одной галочкой. Cron-выражений в v1 нет.

## 23. Синхронизация статусов

Отклик — не конец истории. Задача `SYNC_STATUS` запускается по кнопке «Обновить статусы» и в начале каждого прогона.

Что проверяется:

```
для каждого отклика из applications за последние 60 дней:
    открыть страницу отклика на HH
    прочитать статус: просмотрен / приглашение / отказ / без ответа
    записать в applications.hh_status, hh_status_checked_at

для вакансий со статусом «готова» и «на проверке»:
    проверить, не в архиве ли вакансия
    в архиве → is_closed = true, статус «Вакансия закрыта»
```

Без этого воронка (§28) не работает: показатели «просмотрено / приглашение» брать неоткуда.

### Хранение состояния

Компоненты PrimeVue: DataTable, Column, Button, Tag, Badge, InputText, InputNumber, Select, MultiSelect, Slider, DatePicker, Dialog, Drawer, Tabs, Textarea, Toast, ConfirmDialog, Skeleton, Paginator, ProgressBar, Menu, Tooltip. Иконки — `lucide-vue-next`.

## 28. Статистика

Воронка:

```
Найдено → Прошло фильтры → Подходящих → Откликов → Просмотрено → Приглашений
```

Последние два берутся из `applications.hh_status` (§23). Собеседования и офферы отмечаются вручную.

Технологии: топ требований по вакансиям; отдельно — **требования, которых нет в резюме** (это самое полезное).

Зарплаты: минимум, максимум, среднее, медиана по прошедшим фильтр.

Конверсия: доля просмотров, доля приглашений. По каждому резюме отдельно, чтобы сравнивать.

## 31. Фазы

После каждой фазы проект должен запускаться и быть полезным.

**Фаза 1 — каркас.** FastAPI, SQLite, SQLAlchemy, Alembic, Vue 3, PrimeVue, Tailwind, роутер, TanStack Query. Экран резюме: создание, текст, allowed facts.

**Фаза 2 — LLM-слой.** Интерфейс провайдера, реализации `ollama` и `cli`, экран провайдеров и маршрутизации, кнопка «Проверить». Выжимка резюме. С этого момента `claude -p` и локальная модель уже работают.

**Фаза 3 — браузер.** Persistent Chromium, определение логина, экран «Браузер», статус сессии.

**Фаза 4 — сбор.** Поисковые профили, поиск на HH, сбор hh_id из выдачи, дедупликация, открытие карточки, извлечение JSON с фолбэком на DOM, сохранение, таблица вакансий со ссылками на HH.

**Фаза 5 — фильтры.** Зарплата с валютами и gross/net, формат, опыт, свежесть, ключевые слова, правила компаний, жёсткие правила скам-детекта, причины отклонения, кнопка «Пересмотреть отклонённые».

**Фаза 6 — анализ.** Промпт анализа, схема, валидация, повторная попытка, скор, подозрительность, скрытые инструкции, экран анализа в карточке, экран «Подозрительные».

**Фаза 7 — письма.** Примеры писем, генерация, версии, перегенерация с инструкциями, ручное написание, словарная и LLM-проверка фактов, проверка выполнения скрытых инструкций.

**Фаза 8 — ручной отклик.** Открытие формы, вставка письма, отправка, идемпотентность, история откликов, `DRY_RUN` и `LIVE`. **С этого момента приложением уже можно пользоваться каждый день.**

**Фаза 9 — прогоны.** Персистентная очередь, воркер, запуск/пауза/продолжение/остановка, остановка после 5 ошибок, лента активности через polling, восстановление после падения, лимиты и задержки.

**Фаза 10 — режимы.** Полуавтомат, очередь проверки, автомат со всеми условиями, ответы на вопросы работодателя.

**Фаза 11 — итоги.** Синхронизация статусов откликов, воронка, статистика по технологиям и зарплатам, резервные копии, экспорт.

Внешние провайдеры (`anthropic`, `openai`, `openrouter`) можно добавить в любой момент после фазы 2 — интерфейс уже готов.

## 32. Критерии готовности первой рабочей версии

Версия считается рабочей после фазы 8, когда выполняется всё:

```
 1. Backend и frontend поднимаются локально одной командой каждый
 2. Alembic создаёт схему с нуля
 3. Можно создать резюме, вставить текст, собрать выжимку и поправить её руками
 4. Можно настроить провайдеров и маршрутизацию по шагам, «Проверить» отвечает
 5. Открывается видимый Chromium, пользователь входит в HH руками
 6. Сессия переживает перезапуск приложения
 7. Можно создать поисковый профиль и запустить поиск
 8. Найденные вакансии сохраняются, повторный hh_id не создаёт дубль
 9. В таблице видны название, компания, зарплата, статус и ссылка на HH
10. Фильтры зарплаты, формата, свежести и стоп-слов работают
11. Правило компании CONTAINS «vash» отправляет вакансию в отклонённые
12. Подозрительная вакансия помечается и не теряется
13. Вакансию можно проанализировать, ответ модели валидируется
14. Оценка, причина и отсутствующие навыки видны в карточке
15. Скрытые инструкции из описания находятся и показываются
16. Письмо можно написать самому и сгенерировать моделью
17. Версии писем сохраняются, видно какая отправлена
18. Проверка фактов работает и блокирует отправку при провале
19. Отклик отправляется по кнопке, письмо вставляется в форму
20. Повторный отклик на ту же вакансию невозможен
21. Режим DRY_RUN доходит до формы, но не отправляет
22. История откликов сохраняется и переживает перезапуск
```

## 33. Правила для AI coding agent

1. Прочитать этот документ целиком, затем составить план реализации и показать его.
2. Работать фазами из §31. После каждой фазы проект запускается.
3. Не делать «god class». Слои из §4 не смешивать.
4. Type hints везде. Pydantic для всех внешних данных и всех ответов модели.
5. Все изменения схемы — только через Alembic.
6. Не хардкодить: резюме, модель, провайдера, правила компаний, промпты, пороги.
7. Все селекторы HH — только в `browser/selectors.py`.
8. Frontend ходит только в собственный API. Ни в Ollama, ни в SQLite, ни на hh.kz.
9. Все переходы состояний писать в БД, а не держать в памяти.
10. Реальная отправка отклика — идемпотентна, см. §21.
11. Не обходить капчу и антибот-защиту. Не подменять fingerprint.
12. Не автоматизировать веб-интерфейсы chatgpt.com и claude.ai.
13. Не выдумывать факты о кандидате ни в одном промпте.
14. Не заполнять поля с личными данными (§19).
15. Не отправлять отклик в неизвестном состоянии браузера.
16. Тексты интерфейса — на русском. Коды в БД — на английском.
17. Создать README, `.env.example`, `.gitignore`.
18. Промпты по умолчанию — в `backend/app/prompts/*.md`, загружаются в БД при первом старте.
19. Тесты из §30 писать вместе с кодом соответствующей фазы, не «потом».
20. Демо-данные — опциональный seed, не production-значения в коде.
